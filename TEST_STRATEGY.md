# CardDemo Migration Test Strategy

## Overview

This document defines the testing approach for migrating the CardDemo COBOL application to Java. The strategy ensures functional equivalence between the legacy COBOL system and the new Java implementation through four complementary testing layers.

---

## 1. Golden-File Tests

### Purpose
Capture the exact output of the COBOL system for known inputs, then verify the Java implementation produces byte-identical results.

### Programs to Capture

| Program | Input Files | Output Files | Priority |
|---|---|---|---|
| **CBACT01C** | ACCTDAT | OUTFILE (PSCOMP), ARRYFILE (ARRYPS), VBRCFILE (VBPS) | High — already rewritten |
| **CBACT02C** | CARDDAT | SYSOUT (display) | Medium |
| **CBACT03C** | CCXREF | SYSOUT (display) | Medium |
| **CBCUS01C** | CUSTDAT | SYSOUT (display) | Medium |
| **CBTRN02C** | DALYTRAN, CCXREF, ACCTDAT | TRANSACT (updated), TCATBALF (updated), DALYREJS (new) | Critical |
| **CBTRN03C** | TRANSACT, CCXREF, TRANTYPE, TRANCATG | Report output (SYSOUT) | High |
| **CBACT04C** | TCATBALF, CCXREF, ACCTDAT, DISCGRP | TRANSACT (interest transactions) | Critical |
| **CBSTM03A/B** | TRANSACT (re-keyed), CCXREF, ACCTDAT, CUSTDAT | STATEMNT.PS (text), STATEMNT.HTML | High |

### Input Data Sets

The golden-file inputs are the 9 ASCII data files in `app/data/ASCII/`:

| File | Copybook | Record Length | Records | Description |
|---|---|---|---|---|
| acctdata.txt | CVACT01Y | 300 | 50 | Account master |
| carddata.txt | CVACT02Y | 150 | 50 | Credit cards |
| cardxref.txt | CVACT03Y | 50 (36 usable) | 50 | Card-to-account-to-customer cross-reference |
| custdata.txt | CVCUS01Y | 500 | 50 | Customer records |
| dailytran.txt | CVTRA06Y | 350 | 300 | Daily transactions (pending posting) |
| discgrp.txt | CVTRA02Y | 50 | 51 | Disclosure group interest rates |
| tcatbal.txt | CVTRA01Y | 50 (51 w/ CR) | 50 | Transaction category balances |
| trancatg.txt | CVTRA04Y | 60 | 18 | Transaction category definitions |
| trantype.txt | CVTRA03Y | 60 | 7 | Transaction type definitions |

### Comparison Method

1. **Structured JSON golden files** — Parse each ASCII data file using copybook field layouts into JSON. The JSON serves as a human-readable reference and a machine-comparable format.
2. **Field-by-field diff** — Compare Java output against golden file field-by-field, reporting mismatches with field name, position, expected value, and actual value.
3. **Numeric tolerance** — For signed decimal fields (PIC S9(n)V99), compare using `BigDecimal.compareTo()` to handle trailing-zero differences. For interest calculations (CBACT04C), require exact match (no tolerance) since COBOL truncation must be replicated precisely.

### How to Generate Golden Files

Since the COBOL programs cannot run in this environment (they require z/OS CICS or AWS Mainframe Modernization runtime), golden files are generated by:
1. Parsing the ASCII input data using copybook layouts (the test-harness parser)
2. Applying known business rules documented in the COBOL source (e.g., CBACT01C's cycDebit substitution)
3. For batch programs with complex logic (CBTRN02C, CBACT04C), golden outputs should be captured from a mainframe or AWS M2 run and stored in `golden-files/outputs/`

## 2. Differential Tests

### Purpose
Run the COBOL implementation and Java implementation side-by-side with identical inputs, then compare outputs field-by-field.

### Architecture

```
                    ┌─────────────────┐
  Input Data ──────►│  COBOL Runtime   │──────► COBOL Output
  (ASCII files)     │  (AWS M2 / z/OS) │         (captured)
                    └─────────────────┘
                                                    │
                    ┌─────────────────┐              ▼
  Input Data ──────►│  Java Runtime    │──────► ┌──────────┐
  (same files)      │  (JVM 17+)      │──────► │  Differ  │
                    └─────────────────┘        │  Utility  │
                                               └──────────┘
                                                    │
                                                    ▼
                                             Mismatch Report
```

### Execution Modes

1. **Offline differential** — Compare pre-captured COBOL output files against Java output. Use when mainframe access is unavailable.
2. **Live differential** — Trigger COBOL execution (via JCL submission on AWS M2) and Java execution in parallel, then diff results. Use during parallel-run validation.

### Comparison Granularity

| Level | What's Compared | When to Use |
|---|---|---|
| **Byte-level** | Raw file content (`diff` or `cmp`) | Simple read/display programs (CBACT02C, CBACT03C) |
| **Field-level** | Parsed fields compared by name and type | Programs with reformatting (CBACT01C — date conversion) |
| **Semantic-level** | Business-meaningful aggregates (totals, counts) | Complex batch jobs (CBTRN02C — posted vs. rejected counts) |

### Key Differential Test Scenarios

| Scenario | Input | Expected Behavior |
|---|---|---|
| All accounts, zero cycDebit | acctdata.txt (50 records, all cycDebit=0) | Java substitutes 2525.00 for all records |
| Daily transaction posting | dailytran.txt (300 records) | Same records posted/rejected, same balance updates |
| Interest calculation | tcatbal.txt + discgrp.txt + acctdata.txt | Same interest amounts (exact — no rounding tolerance) |
| Statement generation | transact (re-keyed) + all reference files | Character-identical text and HTML output |
| Empty input | Zero-byte input file | Zero output records, clean exit (no abend) |
| Invalid card in xref | Daily transaction with non-existent card number | Transaction written to DALYREJS, not TRANSACT |

## 3. Batch Reconciliation

### Purpose
After each batch run, verify aggregate metrics to catch data loss, duplication, or calculation errors.

### Reconciliation Checks by Job

#### POSTTRAN (CBTRN02C — Daily Transaction Posting)
```
CHECK 1: Record count conservation
  Input:  COUNT(DALYTRAN records)
  Output: COUNT(TRANSACT new records) + COUNT(DALYREJS records) = COUNT(DALYTRAN)

CHECK 2: Balance integrity
  SUM(ACCTDAT.ACCT-CURR-BAL after) - SUM(ACCTDAT.ACCT-CURR-BAL before)
    = SUM(DALYTRAN.AMT for posted transactions)

CHECK 3: Category balance update
  For each posted transaction:
    TCATBALF[acct-id, type-cd, cat-cd].balance_after
      = TCATBALF[...].balance_before + transaction amount

CHECK 4: Referential integrity of rejections
  Every record in DALYREJS has a card number NOT in CCXREF
  OR the resolved account is NOT in ACCTDAT
  OR the account is not active
```

#### INTCALC (CBACT04C — Interest Calculation)
```
CHECK 1: Interest transaction count
  COUNT(output TRANSACT records) = COUNT(TCATBALF records with non-zero balance)

CHECK 2: Interest rate application
  For each TCATBALF record:
    interest = TRUNCATE(balance × rate / 1200, 2)  -- COBOL truncation, not rounding
    rate = DISCGRP[group-id, type-cd, cat-cd].DIS-INT-RATE

CHECK 3: Cross-reference chain integrity
  Every TCATBALF.ACCT-ID exists in ACCTDAT
  ACCTDAT.ACCT-GROUP-ID matches DISCGRP key prefix
```

#### CREASTMT (CBSTM03A/B — Statement Generation)
```
CHECK 1: Statement count
  COUNT(statements in output) = COUNT(distinct cards in CCXREF)

CHECK 2: Transaction completeness per statement
  For each card: COUNT(transactions on statement) = COUNT(TRANSACT records for that card)

CHECK 3: Balance reconciliation
  Statement ending balance = ACCTDAT.ACCT-CURR-BAL for that account
```

#### READACCT (CBACT01C — Account Reader)
```
CHECK 1: Record count
  COUNT(OUTFILE records) = COUNT(ARRYFILE records) = COUNT(ACCTDAT records)
  COUNT(VBRCFILE records) = 2 × COUNT(ACCTDAT records)

CHECK 2: cycDebit substitution
  For each record where ACCTDAT.ACCT-CURR-CYC-DEBIT = 0:
    OUTFILE.OUT-ACCT-CURR-CYC-DEBIT = 2525.00
```

### Checksum Methodology

For each batch run, compute:
- **Record count** per output file
- **Numeric field sums** for all monetary fields (ACCT-CURR-BAL, TRAN-AMT, etc.)
- **Hash** of key fields (account IDs, transaction IDs) to detect ordering differences
- **Cross-reference integrity** — every foreign key resolves to a valid record

## 4. Contract Tests

### Purpose
Codify the file formats, record layouts, and interface contracts so that any change in the Java implementation that breaks compatibility is detected immediately.

### File Format Contracts

| File | Record Length | Key Fields | Key Position | Organization |
|---|---|---|---|---|
| ACCTDAT | 300 bytes | ACCT-ID (PIC 9(11)) | Bytes 1–11 | KSDS |
| CARDDAT | 150 bytes | CARD-NUM (PIC X(16)) | Bytes 1–16 | KSDS |
| CCXREF | 50 bytes | XREF-CARD-NUM (PIC X(16)) | Bytes 1–16 | KSDS |
| CUSTDAT | 500 bytes | CUST-ID (PIC 9(09)) | Bytes 1–9 | KSDS |
| TRANSACT | 350 bytes | TRAN-ID (PIC X(16)) | Bytes 1–16 | KSDS |
| DALYTRAN | 350 bytes | DALYTRAN-ID (PIC X(16)) | Bytes 1–16 | Sequential |
| TCATBALF | 50 bytes | ACCT-ID+TYPE-CD+CAT-CD | Bytes 1–17 | KSDS |
| DISCGRP | 50 bytes | GROUP-ID+TYPE-CD+CAT-CD | Bytes 1–16 | KSDS |
| TRANTYPE | 60 bytes | TRAN-TYPE (PIC X(02)) | Bytes 1–2 | KSDS |
| TRANCATG | 60 bytes | TYPE-CD+CAT-CD | Bytes 1–6 | KSDS |

### Signed Decimal Contract (Zoned Decimal — DISPLAY format)

Fields with PIC S9(n)V99 use trailing sign overpunch in ASCII data:
```
Positive: { = +0, A = +1, B = +2, C = +3, D = +4, E = +5, F = +6, G = +7, H = +8, I = +9
Negative: } = -0, J = -1, K = -2, L = -3, M = -4, N = -5, O = -6, P = -7, Q = -8, R = -9
Plain digit (0-9): treated as positive, no sign
```

### Interface Contracts to Codify

1. **COBDATFT date conversion** — Input: YYYY-MM-DD → Output: YYYYMMDD (and reverse). Invalid dates (e.g., 2025-02-30) should be rejected.
2. **CEEDAYS date validation** — A date is valid if `java.time.LocalDate.parse()` succeeds with the same format.
3. **CBTRN02C rejection criteria** — A transaction is rejected if: (a) card number not found in CCXREF, (b) account not found in ACCTDAT, or (c) account status is not 'Y'.
4. **CBACT04C interest truncation** — Interest = TRUNCATE(balance × rate / 1200, 2 decimal places). Uses `RoundingMode.DOWN`, not `HALF_UP`.

## Test Execution

### Quick Smoke Test
```bash
cd test-harness
python -m pytest tests/ -v --tb=short
```

### Full Reconciliation
```bash
python -m test_harness.reconciliation ../app/data/ASCII/
```

### Generate Golden Files
```bash
python -m test_harness.golden_file_generator ../app/data/ASCII/ ../golden-files/
```

### Field-Level Diff
```bash
python -m test_harness.differ golden-files/acctdata.json java-output/acctdata.json --layout CVACT01Y
```
